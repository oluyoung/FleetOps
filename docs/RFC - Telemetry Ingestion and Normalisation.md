# RFC: Telemetry Ingestion and Normalisation

## Status

Accepted

## Problem

FleetOps consumes heterogeneous telemetry from OpenSky, Open-Meteo and MQTT. Each provider has different schemas, units, identifiers and delivery mechanisms.

Provider-specific structures should not leak into the domain or frontend.

OpenSky is being used as a public moving-object telemetry source for the demo; the architecture does not assume the source is literally an autonomous industrial vehicle.

MQTT will be used to demonstrate a genuine streaming ingestion path. Vehicle-health values may initially be generated by a controlled producer where no suitable public IoT feed maps cleanly to the same vehicle.

## Proposed Design

```text
OpenSky     Open-Meteo     MQTT
   ↓            ↓            ↓
Provider Adapters
        ↓
CanonicalTelemetryEvent
        ↓
Event Bus
        ↓
Vehicle / Mission / Alert processing
```

Polling and streaming providers have separate transport interfaces but produce the same canonical event model.

Example:

```ts
type CanonicalTelemetryEvent = {
  eventId: string;
  vehicleId: string;
  source: "opensky" | "weather" | "iot";
  occurredAt: string;
  receivedAt: string;
  telemetry: {
    position?: {
      latitude: number;
      longitude: number;
    };
    speedKph?: number;
    headingDegrees?: number;
    batteryPercent?: number;
    motorTemperatureC?: number;
  };
};
```

## Key Decisions

* Provider adapters own validation, unit conversion and schema mapping.
* FleetOps IDs remain independent of provider IDs.
* `occurredAt` and `receivedAt` are stored separately to measure ingestion lag.
* Invalid payloads are rejected before entering the domain.
* Transient provider failures use bounded retry/backoff.
* Providers fail independently.
* Weather is enrichment and must not block primary telemetry.
* Raw high-frequency telemetry is not retained indefinitely in the MVP.

## Alternatives Considered

**Use provider schemas directly** — rejected because it couples the domain to external vendors.

**One microservice per provider** — unnecessary for current scale.

**Kafka from day one** — adds operational complexity without an immediate requirement.

## Trade-offs

The adapter layer introduces mapping code, but it gives the rest of the system stable contracts and makes providers replaceable.

## Success Criteria

The design is successful when:

* OpenSky and MQTT can both produce canonical telemetry events;
* domain services contain no provider-specific logic;
* one provider failing does not stop the others;
* malformed and duplicate events are handled safely.
